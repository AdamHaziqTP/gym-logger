## 2. Correction 2 — Handle-only iOS native-selection hardening

The three-dot drag handle now behaves only as an interactive control; nothing outside the handle changed:

| Treatment | Where | Purpose |
|---|---|---|
| `-webkit-user-select: none; user-select: none` | `.row-handle` (styles.css) | Dots can never become selectable text / selection-handle anchor |
| `-webkit-touch-callout: none` | `.row-handle` | No iOS long-press callout on press/hold |
| `-webkit-user-drag: none` + `draggable={false}` | `.row-handle` + button attr | Never an HTML5/browser drag source |
| `onContextMenu → preventDefault()` | handle button (SessionView.tsx) | Long-press/right-click opens no context menu/callout |
| `-webkit-tap-highlight-color: transparent` | `.row-handle` | No tap flash artifact during press-drag |
| `touch-action: none` | `.row-handle` | Already present (FIX-04); vertical press belongs to reorder, not scroll |

Preserved behaviors (asserted by untouched/green tests):

- Tap → select row; tap selected handle → row menu (C2–C4) — `first tap selects… second tap opens…` test.
- Press/drag past threshold → live preview + normalized single-order commit, data/highlight invariants intact (C5) — pointer-driven drag test.
- Editable cells (`.cell-input`) and Notes (`.notes-input`) keep normal selection/editing: the stylesheet scan proves **no rule other than `.row-handle` declares any `user-select`**, and the DOM test proves a cell input neither prevents context menu nor locks dragging. There is no global text-selection change anywhere.
