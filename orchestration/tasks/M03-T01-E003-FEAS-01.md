# M03-T01-E003-FEAS-01 — bounded Apple Notes color interoperability spike

## Authority and limits

This is the one bounded feasibility spike authorized by E-003 on 2026-08-25.
The target remains the iPhone-first PWA with Apple Notes as canonical archive.

Do not:

- rewrite the product as native;
- add a paid Apple Developer subscription or recurring fragile install;
- change the accepted `Copy to Notes` behavior;
- replace the editable table with an image;
- start M03-T02 or any unrelated milestone.

## Objective

Produce the smallest testable artifact set that compares the authorized routes:

1. PWA → iOS Share Sheet / Shortcuts / Notes handoff;
2. RTF/attributed clipboard or file handoff;
3. only if technically necessary, document whether a minimal native helper
   proof would be required — do not build a native app in this task.

Success requires target-iPhone evidence of a real editable Apple Notes table,
correct values/order, and usable Arms/Back/Chest/Delts/Legs colors. A colored
image, screenshot, PDF, or non-editable attachment is not success.

## Required implementation

Create an isolated feasibility harness under
`orchestration/feasibility/M03-T01-E003/` and/or a clearly marked static test
asset under `public/feasibility/`; do not alter the production Copy to Notes
path unless a shared pure generator is needed and independently covered.

The harness should:

- use a small representative fixture containing all five categories, one
  `none` row, weird free-form values, table order, and notes;
- offer a trusted-HTTPS test page that can generate/download an RTF or other
  attributed-text file handoff and, where supported, invoke the iOS Share
  Sheet with that file;
- probe any browser clipboard representation only if the browser accepts it,
  reporting unsupported/rejected types honestly;
- include precise Shortcuts/Share Sheet instructions if a user-created
  Shortcut is required; do not pretend a Shortcut exists unless it is actually
  supplied and testable;
- preserve plain text and the existing HTML path as controls.

If an RTF generator is implemented, keep it pure/deterministic and test table
rows, cell text escaping, foreground colors, background/highlight colors, and
the five-category mapping. Do not claim that RTF will import into Notes until
the iPhone test proves it.

## Automated acceptance criteria

- Existing suite remains green.
- Feasibility artifacts are isolated, clearly labeled experimental, and do not
  change production Copy to Notes behavior.
- Any RTF/attributed output is deterministic, escaped, and has no external
  dependency or image-only fallback masquerading as success.
- The harness reports route capability honestly; unsupported browser/native
  features are evidence, not hidden failures.
- `npm test -- --run --reporter=dot`, `npm run build`, and `git diff --check`
  pass.
- Write `orchestration/reports/M03-T01-E003-FEAS-01.md` with:
  implementation scope, route comparison, exact iPhone checklist, known
  limitations, and an explicit stop condition if no low-friction route is
  demonstrated.

## Human gate after Codex review

Only after Codex verifies the harness should the user test the available route
on the iPhone 14 Pro Max over trusted HTTPS. Record separately:

- real editable table;
- values/order;
- five category foreground/highlight colors;
- whether the route requires Shortcuts setup, a file handoff, or a native
  install;
- whether it introduces a paid Developer dependency or recurring friction.

If no route passes, stop this spike and return the evidence to the product
bridge. The default next disposition is acceptance of the current editable
rich-table paste without colors as a documented iOS/Notes limitation, while
retaining the working plain-text fallback.
