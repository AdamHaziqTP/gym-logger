## 1. Diagnosis

- Trusted HTTPS retests on the iPhone 14 Pro Max (FIX-02 record): the native
  editable Notes table and all values survive, but **every** category
  foreground AND text-highlight color is stripped when the only encoding is
  modern inline CSS whose backgrounds are translucent `rgba(...)` values.
- WebKit's HTML→attributed-string paste conversion privileges text-run-level
  formatting and legacy attributes; it cannot express translucency and has now
  twice dropped the encodings FIX-01/FIX-02 relied on (`<tr>` styles, then
  per-cell/per-span CSS with `rgba(...)` backgrounds).
- Correction (per the task's required direction):
  1. add an **opaque** highlight representation for the text run — each
     category's locked `rgba(r, g, b, a)` background composited (standard
     source-over) over `#000000`, the payload's actual dark presentation
     backdrop, so visual intent is preserved by construction;
  2. add conservative **legacy-compatible markup** alongside the inline CSS:
     `<font color="#…">` around the text and `bgcolor="#…"` /
     solid `background-color` for the highlight;
  3. keep all layers stating the SAME two colors per category so whichever
     layer the importer honors yields the identical result;
  4. change nothing else: taxonomy, legend, table structure, content order,
     escaping, determinism, clipboard contract, and plain fallback untouched.

## 2. The five mappings (single source of truth)

Locked inputs stay in `HIGHLIGHT_TOKENS` (`src/domain/highlights.ts`),
unchanged and still used verbatim by the app UI. The payload's opaque
backgrounds are computed from them at module load:

| Category | Locked fg (payload + UI) | Locked bg (UI only) | Derived opaque payload bg |
|---|---|---|---|
| Arms (orange) | `#ff9f0a` | `rgba(255, 159, 10, 0.15)` | `#261802` |
| Back (purple) | `#bf5af2` | `rgba(191, 90, 242, 0.16)` | `#1f0e27` |
| Chest (mint) | `#66d4cf` | `rgba(102, 212, 207, 0.15)` | `#0f201f` |
| Delts (blue) | `#0a84ff` | `rgba(10, 132, 255, 0.16)` | `#021529` |
| Legs (pink) | `#ff375f` | `rgba(255, 55, 95, 0.15)` | `#26080e` |

Derivation chain in `highlights.ts`: `PRESENTATION_BACKDROP = "#000000"` →
`parseColorToken()` (`#rrggbb` / `rgba(...)` only; rejects everything else) →
`compositeOverBackdrop()` → `OPAQUE_HIGHLIGHT_BG`, built from
`CATEGORY_LEGEND` so a sixth category could never silently lack an equivalent.
`none` has no entry and produces no color markup anywhere.

## 4. Representative emitted markup (one Arms row cell)

```html
<td bgcolor="#261802" style="padding:4px 8px;vertical-align:top;background-color:#261802;color:#ff9f0a"><font color="#ff9f0a"><span style="color:#ff9f0a;background-color:#261802">Recline curl bench 30° IR uni</span></font></td>
```

`none` rows emit exactly what they always did:
`<tr><td style="padding:4px 8px;vertical-align:top">…</td>…</tr>` — no color,
no attribute, no wrapper.

## 5. Alternatives considered and rejected

- **Keep `rgba(...)` on the cell, opaque only on the text run**: creates two
  different claimed highlights per row, so an importer honoring the cell layer
  would reproduce the exact translucency that already failed twice. The opaque
  values are the identical visual intent over the payload's black backdrop,
  so consistency across layers was strictly safer.
- **Hand-written hex constants**: rejected — a second source of truth that
  could drift from the locked tokens; derivation is enforced by tests.
- **`bgcolor` on `<span>`**: not valid HTML; the solid highlight rides the
  valid `bgcolor` attribute on `<td>` and inline CSS on both levels instead.
- **RTF/native packaging, images, external CSS/classes, a sixth legend item,
  product or sharing redesign**: out of scope per task constraints; none
  introduced.
