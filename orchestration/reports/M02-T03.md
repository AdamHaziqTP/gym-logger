## 1. Summary

Implemented safe whole-session deletion (spec §§11.4, 27.8; acceptance check F6) inside the existing product flow, with no product redesign:

1. **Entry point:** a quiet destructive `Delete Session` row at the end of the existing `SessionView` screen (below Notes) — the least disruptive placement, because SessionView is already reached for every historical session from History (M02-T01) and for the current session from Home/direct resume. Both historical and current sessions are therefore covered by one affordance.
2. **Confirmation:** the action only arms an iOS-style alert dialog (`role="alertdialog"`, modal, backdrop-dismissable) whose entire text content is the exact specified sentence: `Delete this session from Gym Log? This does not affect your Apple Notes archive.` — rendered verbatim in ONE element so the required wording cannot drift.
3. **Cancel/backdrop:** dismisses without any database write and without changing navigation; the same session view stays open with its record byte-for-byte intact.
4. **Confirm:** calls a new transactional `deleteSession(db, sessionId)` data operation (existence check + removal inside one read-write transaction), then returns via the existing `onBack` routing: History when opened from History, Home otherwise — never a stale deleted-session view. Other sessions and all Apple Notes-related copy are untouched; no recycle bin or whole-session undo was added.

Row-level delete/undo (§7.4) is unchanged, as required.

## 3. Placement and behavior decisions (documented per task)

- **Placement (AC-01):** inside `SessionView`, not per-row in the History list. A list-row swipe/button would add a gesture system to a screen whose rows currently do exactly one thing (open); the session screen already scopes actions to one session and is shared by historical and current sessions. The trigger sits below Notes where training-time actions are finished.
- **Dialog content:** the specified sentence is the whole alert (no additional title/message split), so the required Apple Notes-safe copy is present exactly and completely. Buttons: `Cancel` (secondary), `Delete Session` (destructive).
- **Return target (AC-04):** reuse of the established `from: "home" | "history"` back routing. Deleting a session opened from History lands on History; deleting today's resumed/current session lands on Home (which then offers `Start Today's Session` again). Both are stable pre-existing screens; the deleted record is gone from whichever list is shown (live queries).
- **Transactional safety (AC-05):** existence check + delete inside one read-write transaction; racing autosaves are harmless (they no-op on a missing record). No unrelated record can be mutated by construction — the operation touches exactly one key.

3. If the very last remaining session is deleted, Home shows the standard empty state with `Start Today's Session` disabled until another session exists (existing Home logic; unchanged by this task and not separately asserted).
4. IndexedDB is faked (`fake-indexeddb`) in the automated suite; transaction semantics are covered logically, not against Safari/WebKit storage.
