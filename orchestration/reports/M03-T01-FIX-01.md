## 1. Diagnosis (both investigation targets confirmed)

**Target 1 — Async Clipboard availability on a non-secure LAN origin.**
`navigator.clipboard` (and therefore `write()` and `writeText()`) exists only
in secure contexts. The product owner tested `http://192.168.1.49:5173` — a
plain HTTP LAN origin (`isSecureContext === false`). In the pre-FIX code,
`writeNotesPayloadToClipboard` had exactly two mechanisms, both Async
Clipboard: the combined `ClipboardItem` write and `clipboard.writeText`.
On that device both were structurally unavailable, so the function could only
resolve `"failed"` and the UI showed `Copy failed — clipboard unavailable`.
This was a deterministic consequence of serving over HTTP, independent of any
user permission choice. The spec itself names the missing third mechanism:
spec §15.5 requires testing "a traditional selected-DOM copy fallback
(`execCommand("copy")` / selection-based approach)", which M03-T01 did not
implement. **Not reclassified as a LAN reachability problem:** the owner
reached the app and pressed the button; the failure is in-browser.

**Target 2 — activation loss behind the awaited save.**
`commandCopyToNotes` did `await flushSaves()` (debounce timers + IndexedDB
writes) plus an awaited `db.sessions.get(sessionId)` BEFORE the first
clipboard call. iOS/Safari binds clipboard permission to transient user
activation and drops it across awaited tasks, so even on a capable secure
origin the delayed write could be denied. Confirmed in code review of
`SessionView.tsx`; the pre-existing report listed this as known limitation 4.

Both contributors are addressed; neither fix weakens truthful reporting.

## 2. Correction implemented

### `src/domain/notesClipboard.ts`

1. New exported `copyTextViaSelection(text): boolean` — the carefully scoped
   legacy fallback:
   - creates ONE temporary `<textarea>` carrying ONLY the payload's plain
     text, off-screen via inline styles (`position:fixed; left:-9999px`,
     1×1, opacity 0), `aria-hidden`, `readonly`, `tabindex=-1`;
   - focuses/selects it (`select()` + `setSelectionRange(0, length)`), calls
     `document.execCommand("copy")` synchronously — so it stays inside the
     user gesture that started it;
   - removes the helper and RESTORES the previous selection ranges AND focus
     in a `finally` block; nothing unrelated is ever selected or copied;
   - touches no global CSS/user-select state and no editable-table behavior;
   - maps every missing API / throw / refusal to `false`.
2. Attempt order is now rich combined write → async `writeText` → legacy
   selection copy → `"failed"`. The legacy path resolves `"copied-plain"`
   because it can only ever deliver plain text — never misreported as rich
   success (AC-02/AC-03).
3. Documented caller contract: invoke the writer directly inside the tap
   gesture with NO awaited work before it.

### `src/components/SessionView.tsx`

1. New synchronous `buildVisibleNotesPayload()`: cell inputs and the notes
   textarea are uncontrolled, so their live DOM values are merged over the
   session record (keyed by `data-row-id`, columns in screen order) before
   `buildNotesPayload` runs. Latest visible edits are captured verbatim at
   tap time without waiting for persistence.
2. `commandCopyToNotes` ordering fixed (FIX-01): payload built synchronously,
   `void flushSaves()` fired WITHOUT being awaited (persistence converges in
   the background; §17.4 data safety unchanged), and the first clipboard
   attempt starts in the same task as the tap. Failure paths unchanged and
   truthful; double-tap guard unchanged.
3. Comments on `flushSaves`/`activeSaves` updated to describe the new
   trigger-and-converge relationship. No table editing, row menu, drag
   reorder, navigation, delete flow, or styling logic touched; no CSS change.

## 7. Known limitations / boundaries

1. **Insecure HTTP origins can never receive the rich representation.** No
   browser mechanism writes `text/html` to the clipboard outside a secure
   context. On the LAN HTTP path the achievable ceiling is the truthful
   plain-text/TSV payload (priority 1 of spec §15.4 — data preserved);
   Notes table structure and category colors must NOT be expected there.
   A rich-paste device verdict additionally requires a secure build (e.g.,
   HTTPS/LAN-HTTPS dev server or installed PWA context). This is a recorded
   platform limitation, not silent success.
2. **`document.execCommand("copy")` is deprecated.** It remains functional
   in current Safari/WebKit and is the only in-browser plain-copy channel on
   insecure origins, but if WebKit removes it, insecure-origin copies return
   to honest failure. Secure-origin rich/plain behavior is unaffected.
3. **Denial-after-await timing:** when the Async API exists but both writes
   reject, the legacy attempt necessarily happens after awaited rejections;
   Safari may have expired activation by then, so honest failure remains
   possible in that specific case (best-effort per task constraints).
4. **Device result unknown.** jsdom cannot execute iOS WebKit clipboard
   semantics; nothing automated proves the iPhone outcome either way.
5. Untouched by design: PNG export, Notes automation, RTF/native packaging,
   backend/cloud services, generic sharing, the five visible categories, the
   deferred M01 physical gate, `copiedToNotesAt`.
